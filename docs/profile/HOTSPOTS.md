# Гарячі місця до оптимізації (лаба 8)

Записано до будь-яких правок коду, за профілями цієї папки:

- `index-before.svg`, `search-before.svg` — flame graph з `py-spy record -r 200`;
- `cProfile` (`python -m cProfile -o out.prof scripts/profile_lab8.py index|search|score`);
- Scalene 2.4 (`scalene run --cpu-only --profile-all scripts/profile_lab8.py --- search 30`) для поділу
  Python / нативний код.

Машина: Intel Xeon @ 2.10GHz, 2 ядра, Linux, Python 3.13.

| що | час |
|---|---:|
| `build_index("data", positions=True)` під cProfile | 9.7 s (без профайлера 4.9 s) |

## 1. `make_snippet` — 92 % часу пошуку

cProfile: 18.4 s власного часу з 33.4 s на 2000 сніпетів, 58 млн викликів `abs`.

Гіпотеза: щоб вибрати найкраще вікно, код для кожного входження терма перебирає всі інші входження
(`len({t for s, _, t in hits if abs(s - start) <= radius})`) — це O(h²). У довгому документі `event` і `loop`
зустрічаються сотні разів, тож на один сніпет — сотні тисяч порівнянь. Це час у Python: цикл по кортежах у
generator expression; Scalene показує рядок 138 у `ranking.py` серед найдорожчих, нативна частина там — лише
створення множин. Друга частина — `normalize()` для кожного слова документа (5.9 млн викликів), теж Python-цикл
навколо нативних `casefold` і `unicodedata.normalize`.

Висновок: скорер узагалі не гаряче місце для типового запиту, гаряче — сніпети. Виправлення — вікно, що ковзає по
входженнях за O(h).

## 2. `tokenize` під час індексації — третина часу `build_index`

cProfile: 3.5 s сукупного часу з 9.7 s, 3.9 млн кроків генератора.

Гіпотеза: регулярний вираз шукає токени в C, але кожен токен — це окремий крок генератора, виклик
`m.group()`, `casefold` і повернення в цикл індексатора. Scalene на рядку `yield m.group()`: 4.4 % Python,
8.5 % нативного коду — тобто приблизно третина цього рядка — накладні витрати інтерпретатора на кожен токен.

## 3. Тіло циклу `index_documents` — 3.7 s власного часу

Гіпотеза: на кожен токен — `term_pos[tok].append(pos)` у `defaultdict` і `length += 1`, на кожну пару
(терм, документ) — `postings[term].append(...)`. 4.8 млн `list.append`. Чистий Python: кожна операція —
пошук у словнику, виклик методу, створення int-об'єкта; NumPy тут не допоможе, бо робота — по рядках.

Окремо: `storage.load` — 2.1 s на старті сервісу, бо створює 840 тис. об'єктів `Posting` з кортежами позицій.
